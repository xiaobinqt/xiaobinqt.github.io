# 旅行地图维护说明

旅行地图的页面地址是 `/travel/`，所有地点保存在当前目录的 [`index.md`](./index.md) 中。

日常维护推荐使用项目自带的 `scripts/travel.py`，不需要手动填写十几个字段。

## 最简单的维护方式

### 首次配置

脚本使用高德 Web 服务查询景点坐标。先在高德开放平台申请一个“Web 服务”类型的 Key，然后在终端配置环境变量：

```bash
export AMAP_WEB_KEY="你的高德 Web 服务 Key"
```

Key 只会从环境变量读取，不会写入旅行页面或提交到 Git 仓库。可以把上面的 `export` 放进自己的 `~/.zshrc`，以后无需重复输入。

如果希望脚本自动生成地点介绍，再配置 OpenAI API Key：

```bash
export OPENAI_API_KEY="你的 OpenAI API Key"
```

配置后，原来的新增命令不需要改变。脚本会使用 OpenAI Responses API 搜索权威资料，生成地点简介、始建年代、历史沿革、典故、现场看点和来源链接。默认模型是 `gpt-5.4-mini`，如需调整可以设置：

```bash
export OPENAI_MODEL="gpt-5.4-mini"
```

OpenAI Key 同样只从环境变量读取，不会写入文章或仓库。调用 AI 会产生少量 API 费用；生成内容是初稿，发布前仍需打开来源链接复核。

### 新增地点

在项目根目录执行：

```bash
./scripts/travel.py add 北京 太庙
```

这条命令表示：记录一次发生在北京太庙的旅行。由于北京是直辖市，可以省略重复的城市参数；其中 `北京` 是省级行政区和城市，`太庙` 是本次记录的具体地点。

如果不增加其他参数，脚本采用以下默认值：

- 旅行日期使用执行命令当天的完整日期。
- 同行人使用 `together`，即“我们俩”。
- `spots` 使用地点名称，这里是“太庙”。
- 自动创建并直接发布旅行文章，不保存为草稿。

执行过程中，脚本会完成以下操作：

1. 使用高德 Web 服务地理编码查询太庙，补全省、市、区县以及 `[经度, 纬度]`。
2. 在写入前显示识别到的地址和坐标，等待确认；结果不正确时输入 `n` 即可取消。
3. 为这次到访生成唯一地点 `id`，并把足迹写入 `content/travel/index.md`。
4. 在 `content/posts/travel/` 创建类似 `YYYY-MM-DD-beijing-taimiao.md` 的旅行文章。
5. 把文章路径写入该足迹的 `article`，使地图上的“阅读这篇游记”可以直接跳转。

这里的“写入”采用原子替换：只有完整的新内容准备成功后才会替换原文件，执行中途失败不会留下只写了一半的 YAML。高德 API Key 只读取环境变量 `AMAP_WEB_KEY`，不会出现在旅行数据、文章或 Git 提交中。手动提供 `--coordinates` 时不会调用高德接口。

北京、上海、天津、重庆、香港和澳门可以使用两个参数：

1. 城市。
2. 景点或具体地点。

普通省市仍然使用三个参数：

```bash
./scripts/travel.py add 浙江省 杭州市 西湖
```

依次填写：

1. 哪个省或直辖市。
2. 哪个城市。
3. 什么地方。

脚本会自动查询并补全：

- 唯一 ID。
- 省、市、区县。
- 经度和纬度。
- 今天的完整日期（也可以用 `--date` 指定旅行日期）。
- 同行人默认值 `together`。
- 景点列表和默认摘要。
- 配置了 `OPENAI_API_KEY` 时，自动生成一份带权威来源的地点介绍初稿。
- 一篇位于 `content/posts/travel/`、默认直接发布的游记。

写入前会显示识别出的地址和坐标，直接按回车确认。如果地点识别错误，输入 `n` 取消，再把地点名称写得更具体。

新增完成后会同时得到两样东西：一条地图足迹，以及一篇 `draft: false` 的 Markdown 游记。地图会立即关联这篇文章。

### 更多新增例子

```bash
# 最简单：我们俩、今天去北京太庙
./scripts/travel.py add 北京 太庙

# 强制使用 AI；没有配置 OPENAI_API_KEY 时直接提示错误
./scripts/travel.py add 北京 太庙 --ai

# 本次不使用 AI，即使终端已经配置了 OPENAI_API_KEY
./scripts/travel.py add 北京 太庙 --no-ai

# 只有我去过
./scripts/travel.py add 四川省 成都市 成都大熊猫繁育研究基地 --who me

# 只有 TA 去过，并指定月份
./scripts/travel.py add 浙江省 杭州市 西湖风景名胜区 --who partner --date 2025-04

# 精确到某一天
./scripts/travel.py add 陕西省 西安市 大唐芙蓉园 --date 2025-10-03

# 一次旅行包含多个景点和一句摘要
./scripts/travel.py add 陕西省 西安市 古城之旅 \
  --date 2025-10 \
  --spot 大雁塔 \
  --spot 西安城墙 \
  --spot 陕西历史博物馆 \
  --note "从城墙走到大雁塔，把长安的秋天慢慢看完。"

# 自定义游记文件名，会生成 content/posts/travel/beijing-autumn.md
./scripts/travel.py add 北京市 北京市 故宫 \
  --date 2024-10 \
  --slug beijing-autumn

# 不申请高德 Key，手动提供坐标和区县
./scripts/travel.py add 上海市 上海市 外滩 \
  --coordinates "121.490,31.241" \
  --district 黄浦区

# 只记录“去过日本”，自动标在国家概览位置
./scripts/travel.py add-world 日本 --who together

# 海外地点建议补充精确坐标
./scripts/travel.py add-world 日本 东京 浅草寺 \
  --coordinates "139.7967,35.7148" \
  --date 2025-04

# 这次只添加地图足迹，不生成文章
./scripts/travel.py add 广东省 深圳市 世界之窗 --no-post

# 已经有一篇旧游记时，直接关联它，不再生成新文章
./scripts/travel.py add 上海市 上海市 外滩 --article /shanghai-trip/
```

海外精确坐标可以使用全球范围内的经纬度。例如巴黎埃菲尔铁塔：

```bash
./scripts/travel.py add-world 法国 巴黎 埃菲尔铁塔 \
  --coordinates "2.2945,48.8584" \
  --date 2025-06
```

### 同一个地方去多次

每次到访都是一条独立足迹和一篇独立游记。文件名包含完整日期，因此多次前往同一个地方不会互相覆盖：

```bash
# 第一次去太庙，生成 2026-09-12-beijing-taimiao.md
./scripts/travel.py add 北京 太庙 --date 2026-09-12

# 第二次去太庙，生成 2027-04-03-beijing-taimiao.md
./scripts/travel.py add 北京 太庙 --date 2027-04-03
```

地图会把它们统计为两次出发，并显示“第 1 次到访”“第 2 次到访”。完全相同的坐标会轻微错开，让每一次都可以点击。

如果同一天确实有两段需要分别记录的独立行程，第二次增加 `--repeat`：

```bash
./scripts/travel.py add 北京 太庙 --date 2026-09-12 --repeat
```

脚本会自动生成 `2026-09-12-beijing-taimiao-2.md` 和新的足迹 ID。没有 `--repeat` 时，脚本会阻止同一天的重复写入，避免误操作。若本来就是同一段行程，更推荐只新增一次，再用多个 `--spot` 记录内容。

### 全年旅行年鉴

旅行页面顶部可以在“旅行地图”和“年度年鉴”两个 Tab 之间切换。年度年鉴会根据现有足迹自动生成，不需要维护新的配置。它会展示：

- 每年的出发次数和不同目的地数量。
- 两个人共同出发的次数。
- 已经完成的游记数量。
- 1～12 月的旅行时间轨迹。
- 当年的全部足迹入口。

点击年份可以切换年鉴；点击某个月份或某条年度足迹，会自动回到地图并打开对应详情。

需要直接分享某个视图时，可以使用：

```text
/travel/#map
/travel/#yearbook
```

年度汇总依赖 `date` 字段，支持下面两种格式：

```yaml
date: "2025-04"
date: "2025-04-18"
```

没有日期的国家级概览足迹仍会出现在世界地图中，但不会进入年度汇总。补上日期后会自动归入对应年份。

### 草稿与发布

新文章默认直接发布，并自动关联地图。如果暂时只想保存草稿，新增时使用：

```bash
./scripts/travel.py add 北京 太庙 --draft
```

草稿写完后，先查看足迹 ID：

```bash
./scripts/travel.py list
```

编辑自动生成的 `content/posts/travel/*.md`。写完后执行：

```bash
./scripts/travel.py publish 地点ID
```

这个命令会一次完成两件事：

1. 把文章的 `draft` 改为 `false`。
2. 自动把地图足迹的 `article` 关联到该文章。

旧版的 `--publish` 参数仍然兼容，但现在默认行为就是直接发布，不再需要主动填写。

### 其他维护命令

```bash
# 查看全部地点及其 ID
./scripts/travel.py list

# 给已有地点补充文章链接，ID 可通过 list 查看
./scripts/travel.py article 地点ID /beijing-trip/

# 删除地点（del 和 remove 完全等价）
./scripts/travel.py del 地点ID

# 同时删除这一次足迹对应的旅行文章
./scripts/travel.py del 地点ID --with-post

# 原命令继续可用
./scripts/travel.py remove 地点ID
```

默认只删除地图中的足迹，文章会继续保留。只有明确增加 `--with-post` 时，脚本才会根据文章 Front Matter 中的 `travel_id` 精确找到并删除对应文章；同一地点去过多次时，不会影响其他次数的记录。删除前会同时显示地点和文章路径，增加 `--yes` 可以跳过确认。文章文件会被直接删除：已提交到 Git 的文件可以从版本历史恢复，尚未提交的文章无法自动恢复。

如果不想申请高德 Key，也可以给国内地点手动提供坐标，此时不会请求外部接口：

```bash
./scripts/travel.py add 北京市 北京市 故宫 --coordinates "116.397,39.916" --district 东城区
```

下面的章节是完整的数据说明和手动维护方法。只有需要填写更多旅行细节，或者脚本无法正确识别地点时才需要阅读。

海外地点不使用高德国内地理编码：`add-world 日本` 会使用国家概览坐标，适合“去过日本”这种国家级记录。填写了城市或景点时，脚本会要求提供 `--coordinates`，避免把东京浅草寺错误地标在日本中心位置。

## 旅行文章放在哪里

所有旅行文章统一保存在：

```text
content/posts/travel/
```

默认文件名由“日期 + 城市拼音 + 地点拼音”组成，既方便识别，也适合作为文章 URL，例如：

```text
content/posts/travel/2026-09-12-beijing-taimiao.md
```

地图内部使用的唯一 ID 不再出现在文件名里，它会继续保存在文章的 `travel_id` 字段中。

macOS 可以直接使用系统提供的拼音转换；其他系统安装项目依赖后即可使用：

```bash
python3 -m pip install -r requirements.txt
```

少数多音字或海外地名的拼写可能不符合预期，可以用 `--slug` 手动覆盖：

```bash
./scripts/travel.py add 北京 太庙 --slug beijing-taimiao
./scripts/travel.py add-world 日本 东京 浅草寺 \
  --coordinates "139.7967,35.7148" \
  --slug tokyo-asakusa
```

也可以在新增时使用 `--slug` 设置更好读的英文文件名：

```bash
./scripts/travel.py add 北京市 北京市 故宫 --slug beijing-autumn
```

脚本在文章 Front Matter 中写入 `travel_id`，用它安全地找到文章。因此不要手动删除或修改这个字段：

```yaml
travel_id: "110101-ab12cd34"
```

因为站点当前对 `posts` 使用文件名作为永久链接，所以文章虽然保存在 `content/posts/travel/`，最终访问地址仍然是 `/beijing-trip/`，不是 `/posts/travel/beijing-trip/`。

### 旅行文章里的地点介绍怎么写

新生成文章的固定顺序是“此行所感”→“行程与照片”→“认识这里”。地点和日期由文章标题展示，不再在正文中重复；可查证的地点背景与个人感受分开记录。

推荐按照下面的顺序维护：

```markdown
## 认识这里

> 用 80～150 字介绍这里：它是什么、为什么值得来，以及它在当地历史或文化中的位置。

- **始建 / 形成**：写清朝代和年份；自然景观写形成原因或首次有文字记载的时间
- **历史沿革**：只保留 2～3 个真正改变这个地点的重要节点
- **经典典故**：写一个与地点直接相关、可以查证的故事；传说要明确写“相传”
- **别错过**：列出 2～4 个现场值得寻找的建筑、展品、景观或细节
- **资料来源**：[查看官方资料](https://example.com/)
```

统一采编规则：

1. 事实和感受分开写。历史介绍保持客观，自己的体验放在“此行所感”。
2. 不确定的年代不要猜。能确认到年份就写年份，只能确认朝代就只写朝代。
3. 区分史实和传说。没有可靠记载的故事使用“相传”“民间传说”等措辞。
4. 不大段复制资料。读完来源后用自己的话概括，地点简介建议控制在 80～150 字。
5. 至少提供一个可点击的来源链接。来源优先级为：景区或博物馆官网、政府文旅或文物保护资料、权威百科；不建议链接营销号和无署名转载文章。
6. 链接文字写清内容，例如“查看故宫博物院官方介绍”，不要只写“点这里”。发布前打开一次，确认链接有效。
7. 海外地点可以链接当地景区官网、国家或城市旅游局页面；外文资料可以用中文概括，但不要自行翻译专有名称。

如果一个地点包含多个景点，在同一个章节中用三级标题拆开：

```markdown
### 太庙

（太庙的小档案）

### 景山公园

（景山公园的小档案）
```

配置了 `OPENAI_API_KEY` 时，脚本会先联网检索并生成这一部分；未配置 Key 或使用 `--no-ai` 时，则生成“待补充”结构。AI 调用异常时，普通新增会安全降级为待补充模板；显式使用 `--ai` 时会停止写入并显示错误，避免误以为内容已经生成。

AI 初稿会带权威来源链接，并在 Markdown 中留下复核提示。它不会读取照片、私人备注或旧游记，只会发送地点名称、行政区、景点列表和你主动提供的参考链接。年代、人物、典故和专有名称仍应在发布前人工确认。

### 多张照片使用旅行图集

“行程与照片”里有多张图片时，用 `travel-gallery` 把普通 Markdown 图片包起来：

```markdown
{{</* travel-gallery label="太庙旅行照片" */>}}
![红墙下的合影](https://example.com/photo-1.jpg "红墙下的合影")

![享殿屋檐](https://example.com/photo-2.jpg "享殿屋檐")

![院中的古柏](https://example.com/photo-3.jpg "院中的古柏")
{{</* /travel-gallery */>}}
```

桌面端会自动排成两列错落的旅行胶片墙，移动端自动变成单列。圆括号末尾引号中的标题用于开启灯箱并显示照片说明，请不要省略；不想显示说明时可以像 `![](图片地址 " ")` 一样保留一个空格。点击图片可以打开灯箱查看原图。`label` 用于无障碍阅读，建议按“地点 + 旅行照片”填写。

不要把技术截图或正文里的单张配图放进这个短代码；它只用于旅行文章中的连续照片。

如果新增时已经找到权威资料，可以直接把链接交给脚本：

```bash
./scripts/travel.py add 北京 太庙 \
  --reference "https://景区或文旅部门的资料页面"
```

这样文章会直接生成“查看官方或权威资料”链接。`--reference` 必须填写以 `https://` 或 `http://` 开头的完整地址；不填写时只显示“资料来源：待补充”，不会生成一个无法打开的占位链接。

## 1. 地点数据结构（进阶）

每个地点的完整配置如下：

```yaml
places:
  - id: beijing-gugong
    name: "北京 · 故宫"
    country: "中国"
    countryCode: "CHN"
    province: "北京市"
    city: "北京市"
    district: "东城区"
    coordinates: [116.397, 39.916]
    date: "2024-10"
    who: together
    spots: ["故宫博物院", "景山公园", "什刹海"]
    note: "沿着中轴线慢慢走，把秋天和红墙都装进照片里。"
    article: "/beijing-trip/"
```

字段说明：

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 地点的唯一标识。建议使用小写英文、数字和短横线，不能与其他地点重复。 |
| `name` | 是 | 地图详情和地点卡片显示的标题。推荐使用“城市 · 地点”的格式。 |
| `country` | 是 | 国家中文名称，例如 `中国`、`日本`。 |
| `countryCode` | 是 | ISO 3166-1 三位国家代码，例如中国 `CHN`、日本 `JPN`。 |
| `province` | 国内必填 | 省、自治区、直辖市或特别行政区的完整名称；海外国家级记录可以为空。 |
| `city` | 建议填写 | 城市名称，例如 `西安市`。 |
| `district` | 可选 | 区、县或市级区域，例如 `雁塔区`。 |
| `coordinates` | 是 | 地图坐标，顺序必须是 `[经度, 纬度]`，不能写反。 |
| `date` | 建议填写 | 旅行时间。可以写 `2024-10`，也可以写完整日期 `2024-10-03`。 |
| `who` | 是 | 同行人分类，只能填写 `together`、`me` 或 `partner`。 |
| `spots` | 可选 | 这次旅行去过的具体景点，可填写一个或多个。 |
| `note` | 可选 | 用作旅行文章的摘要和开篇文字，不在地图详情卡中展示。建议控制在 30～60 个汉字。 |
| `article` | 可选 | 对应游记的站内路径。没有文章时保留空字符串 `""`。 |

## 2. 同行人分类

`who` 决定地图坐标颜色和筛选结果：

```yaml
who: together  # 我们俩一起去过
who: me        # 只有我去过
who: partner   # 只有 TA 去过
```

不要填写中文，也不要使用这三个值以外的内容。

## 3. 手动新增一个地点

打开 [`index.md`](./index.md)，找到 `places:`，复制任意一个完整地点配置，粘贴到列表末尾，再修改内容。

例如新增上海外滩：

```yaml
  - id: shanghai-bund
    name: "上海 · 外滩"
    country: "中国"
    countryCode: "CHN"
    province: "上海市"
    city: "上海市"
    district: "黄浦区"
    coordinates: [121.490, 31.241]
    date: "2025-05-02"
    who: together
    spots: ["外滩", "南京东路", "豫园"]
    note: "从白天走到亮灯，江风和天际线都很难忘。"
    article: "/shanghai-trip/"
```

注意 YAML 缩进：

- `- id` 前面是两个空格。
- 其他字段需要与 `id` 对齐，前面是四个空格。
- 使用英文半角冒号 `:` 和方括号 `[]`。
- 包含特殊符号或冒号的文字建议始终使用双引号。

保存后，地图会自动完成以下更新：

- 在对应经纬度增加坐标。
- 点亮地点所在省份。
- 更新足迹次数、省份和游记数量。
- 生成地点卡片和详情内容。
- 将地点加入对应的同行人筛选结果。
- 在“世界”视图中点亮相应国家。

## 4. 获取经纬度

可以在常用地图中搜索景点，再复制其经纬度。配置时必须按照下面的顺序填写：

```yaml
coordinates: [经度, 纬度]
```

例如北京故宫大约是：

```yaml
coordinates: [116.397, 39.916]
```

中国大陆的经度通常在 `73`～`135` 之间，纬度通常在 `18`～`54` 之间。如果坐标点明显跑到地图外，优先检查经纬度是否写反。

建议坐标保留 3～6 位小数。旅行地图用于展示足迹，不需要使用家庭住址或其他私人精确位置。

海外国家还需要正确填写 `countryCode`。常见示例：

```yaml
country: "日本"
countryCode: "JPN"

country: "美国"
countryCode: "USA"

country: "法国"
countryCode: "FRA"
```

## 5. 关联旅行文章

文章链接填写 Hugo 最终生成的站内路径，不是 Markdown 文件路径。

旅行文章统一放在：

```text
content/posts/travel/shanghai-trip.md
```

按照当前站点的永久链接规则，通常配置为：

```yaml
article: "/shanghai-trip/"
```

配置成功后，地点详情中会出现“阅读这篇游记”按钮。

文章暂时没有写好时使用：

```yaml
article: ""
```

此时页面会显示“游记待补”，不会产生无效链接。文章发布后再补充路径即可。

## 6. 同一城市维护多个地点

如果一次旅行在同一城市去了多个景点，有两种维护方式。

### 方式一：合并成一次旅行

适合属于同一次行程、共用一篇游记的景点：

```yaml
name: "西安 · 古城之旅"
coordinates: [108.964, 34.218]
spots: ["大雁塔", "城墙", "钟楼", "陕西历史博物馆"]
article: "/xian-trip/"
```

地图上显示一个坐标，详情中列出多个景点。

### 方式二：拆成多个坐标

适合不同时间前往、需要分别关联文章，或者希望在地图上展示多个精确位置的情况。每个地点都需要独立的 `id` 和 `coordinates`。

## 7. 修改或删除地点

修改地点时，直接编辑对应字段并保存。

删除地点时，从 `- id:` 开始，删除该地点的整个配置块。不要只删除 `id`，否则可能产生无法识别的记录。

如果修改了 `id`，请确认没有与其他地点重复。

## 9. 常见问题

### 页面有地点卡片，但地图没有显示

地图边界文件可能没有加载成功。检查下面的文件是否存在：

```text
static/data/china-provinces.geojson
```

不要随意修改这个 GeoJSON 文件。如果只是在维护旅行地点，无需改动地图边界数据。

### 地点出现在错误的位置

检查 `coordinates`：

- 是否使用 `[经度, 纬度]` 顺序。
- 是否使用英文逗号。
- 数字外面不要加引号。
- 是否误用了国外地图转换后的坐标。

### 点击地点后没有文章按钮

检查 `article` 是否为空。站内路径建议以 `/` 开头并以 `/` 结尾，例如：

```yaml
article: "/xian-trip/"
```

### 新地点没有点亮对应省份

检查 `province` 是否填写了正确的完整行政区名称。例如：

```yaml
province: "陕西省"
province: "北京市"
province: "内蒙古自治区"
province: "香港特别行政区"
```

### Hugo 提示 YAML 解析失败

通常由缩进、中文标点或未闭合的引号导致。可以先对照现有地点逐行检查，尤其注意：

- 不要使用 Tab 缩进。
- 双引号必须成对出现。
- 数组中的项目使用英文逗号分隔。
- 地点配置必须位于页面开头的两个 `---` 之间。
